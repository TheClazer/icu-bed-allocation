When the bed list is wrong,
a patient waits

In an emergency, families and ambulance crews phone hospital after hospital looking for a free ICU bed.

During the 2021 COVID-19 wave in Bengaluru, availability lists went stale within minutes and beds were reported blocked under false names.

Citizen Matters, 2021: report on the city bed allotment system.

Stale availability

One bed promised twice
Two requests read the same free bed at the same moment, and both book it.

Beds blocked, never used
Holds placed and never converted keep real patients out.
Goal: a shared database that books the nearest suitable bed, can never allot one bed twice, frees unused holds by itself, audits every action, and stays correct through deadlocks and crashes.

Five processes, one source of truth

Two identical, stateless app servers share one MySQL primary. Redis only speeds things up and can be rebuilt from MySQL at any time.

  • MySQL decides
    Every booking, hold and transfer is one InnoDB transaction. Constraints and triggers are the last line of defence.
  • Redis accelerates
    Nearest-hospital search and live counters. Written only after a commit, rebuilt from MySQL if lost.
  • Replica for reading
    GTID asynchronous replication. Reports read here, bookings never do.
  • One command to run
    run.bat starts all five as plain Windows processes. No Docker, no admin rights.

Nine entities, normalised to BCNF

hospitalbed_typebed user_accountpatientbed_request reservationtransferaudit_log
The rule the database enforces itself
active_bed_id INT GENERATED ALWAYS AS
  (CASE WHEN status = 'HELD' THEN bed_id END) STORED,
UNIQUE KEY one_active_booking_per_bed (active_bed_id)

A held reservation copies its bed id into this column; any other status leaves NULL. A second live hold on the same bed breaks the UNIQUE index, even if the application forgets to lock.

5triggers: hold limit, audit, bed release
1event expiring holds every 5 seconds
2views for the audit and the bed board

Booking a bed is one transaction

-- Redis: nearest hospitals with a free bed
GEOSEARCH hospitals:geo FROMLONLAT 77.62 12.93 BYRADIUS 50 km ASC

START TRANSACTION;
SELECT bed_id FROM bed
 WHERE bed_type_id = 1 AND status = 'FREE' AND hospital_id = 7
 ORDER BY bed_id LIMIT 1
   FOR UPDATE SKIP LOCKED;
INSERT INTO reservation (request_id, bed_id, status, hold_expires_at)
 VALUES (55, 703, 'HELD', sim_now() + INTERVAL 30 MINUTE);
UPDATE bed SET status = 'HELD' WHERE bed_id = 703;
COMMIT;

-- only now: refresh the Redis counter from MySQL
SET free:7:1 0

What InnoDB does, shown live

Results and conclusion

50/50race runs with exactly one hold on the last bed
20/20automated tests passing against the live database
4.7 sfrom killing MySQL to a consistent, recovered state
0beds allotted twice, in every scenario tried

Correctness lives in the database, not in the application: row locks, a UNIQUE constraint, triggers, a scheduled event and crash recovery each stop one way a bed could be lost or double-booked.

The same design fits any scarce shared resource, from ambulances to blood units, where two people must never be promised the same thing.
